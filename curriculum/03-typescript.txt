@@module ts-primeiros-passos | ts | Primeiros passos | O que o TypeScript adiciona ao JavaScript e como ler os erros do compilador.

@@lesson ts-por-que | Por que TypeScript? | 15
@@body
**TypeScript (TS)** é JavaScript com **tipos**. Você descreve que forma os dados têm, e o compilador confere o código **antes** de ele rodar. O que o JS descobre só quando o programa quebra na frente do usuário, o TS aponta no editor.

```ts
function dobro(n: number): number {
  return n * 2;
}

dobro(5);      // ok
dobro("5");    // erro: Argument of type 'string' is not assignable to parameter of type 'number'
```

### Ideias centrais

- Todo JS válido é TS válido. Você adota tipos aos poucos.
- Os tipos **somem** na hora de rodar: o compilador gera JavaScript puro. Não existe custo em tempo de execução.
- Em muitos casos você nem precisa escrever tipos: o TS **infere** (`const x = 5` já é `number`).
- Beneficios práticos: autocompletar confiável, refatoração segura, documentação viva e menos bugs em produção.

### Neste site

O editor desta trilha usa o compilador do TypeScript no seu navegador, no **modo estrito** (`strict`). Depois de **Verificar**, você vê:

- **Erros de tipo** do compilador, com a linha. Aprender a ler essas mensagens (em inglês) é uma habilidade profissional.
- **Testes de tipo**: checagens que verificam se os seus tipos têm a forma pedida.
- **Testes de execução**, como na trilha de JS.

> Quando um erro vier longo, leia a **última** linha dele primeiro: costuma ser a causa real.

@@lesson ts-tipos-basicos | Tipos básicos | 20
@@body
### Primitivos

`string`, `number`, `boolean`, `bigint`, `symbol`, `null` e `undefined`. Em modo estrito, `null` e `undefined` **não** cabem em outros tipos por acaso.

### Arrays e tuplas

```ts
const nomes: string[] = ["Ana", "Rui"];          // ou Array<string>
const ponto: [number, number] = [10, 20];        // tupla: tamanho e tipos por posição
const registro: [string, number] = ["Ana", 30];
```

Uma **tupla** é um array de tamanho fixo em que cada posição tem seu tipo.

### `any`, `unknown`, `void` e `never`

- `any`: desliga a checagem. É uma "saída de emergência" que contamina o código. **Evite.**
- `unknown`: "não sei o tipo ainda". Você precisa **verificar** antes de usar. É a alternativa segura ao `any`.
- `void`: função que não devolve nada útil.
- `never`: valor que nunca acontece (função que sempre lança erro, ou ramo impossível).

### Inferência: não anote tudo

```ts
const x = 5;          // tipo: 5 (literal, por ser const)
let y = 5;            // tipo: number
const lista = [1, 2]; // number[]
```

Regra prática: **anote** parâmetros de função e retornos públicos; deixe o TS inferir variáveis locais.

### `as const`

Congela o valor e preserva os literais: `["a", "b"] as const` vira `readonly ["a", "b"]`.
@@task

@@lesson ts-funcoes-tipadas | Funções tipadas | 20
@@body
Em funções, anote os **parâmetros** e, em geral, o **retorno**:

```ts
function formatar(nome: string, sobrenome?: string): string {
  return sobrenome ? `${nome} ${sobrenome}` : nome;
}
```

- `sobrenome?: string` é **opcional**: seu tipo real é `string | undefined`.
- Valor padrão: `function a(x: number = 10)` torna o parâmetro opcional automaticamente.
- Rest: `function somar(...n: number[])`.

### Tipos de função

Dá para descrever a forma de uma função (útil para callbacks):

```ts
type Operacao = (a: number, b: number) => number;

const somar: Operacao = (a, b) => a + b;   // a e b são inferidos como number

function aplicar(fn: (n: number) => number, valor: number): number {
  return fn(valor);
}
```

### `void` e retorno

Um callback tipado como `() => void` pode devolver qualquer coisa que será ignorada. Já uma função anotada com retorno `void` não deve retornar valor.

> **Dica:** sem anotar o retorno, o TS infere. Anotá-lo mesmo assim pega erros onde você **devolve** a coisa errada, não onde a usa.
@@task
Escreva: `formatar(nome, sobrenome?)` devolvendo `"Ana Silva"` (ou só `"Ana"` se não houver sobrenome); `somarTudo(...nums)` com rest de números; o tipo `Operacao` e a constante `multiplicar` usando-o; e `aplicar(fn, valor)` com `fn` tipada como função de número para número.
@@starter
// 1. formatar: sobrenome é opcional

  return "";
}

// 2. somarTudo aceita qualquer quantidade de números
function somarTudo(nums: number[]): number {
  return 0;
}

// 3. defina o tipo Operacao: (a: number, b: number) => number
type Operacao = any;

const multiplicar: Operacao = (a, b) => 0;

// 4. aplicar recebe uma função de number para number
function aplicar(fn: any, valor: number): number {
  return 0;
}
@@tests
$t('formatar("Ana", "Silva") = "Ana Silva"', () => $eq(formatar('Ana', 'Silva'), 'Ana Silva'));
$t('formatar("Ana") = "Ana"', () => $eq(formatar('Ana'), 'Ana'));
$t('somarTudo(1, 2, 3) = 6', () => $eq(somarTudo(1, 2, 3), 6));
$t('somarTudo() = 0', () => $eq(somarTudo(), 0));
$t('multiplicar(6, 7) = 42', () => $eq(multiplicar(6, 7), 42));
$t('aplicar(n => n + 1, 9) = 10', () => $eq(aplicar((n: number) => n + 1, 9), 10));
@@types

## formatar recusa chamada sem argumentos

## somarTudo aceita vários números
somarTudo(1, 2, 3);
## somarTudo recusa texto
// @ts-expect-error
somarTudo("a");

const __c1: __Equal<Operacao, (a: number, b: number) => number> = true;
## aplicar recusa função que recebe texto
// @ts-expect-error

@@hints
- sobrenome?: string torna o parâmetro opcional. Dentro da função, trate o caso undefined.
- Rest parameter: ...nums: number[]
- type Operacao = (a: number, b: number) => number;
- fn: (n: number) => number
@@solution
function formatar(nome: string, sobrenome?: string): string {
  return sobrenome ? `${nome} ${sobrenome}` : nome;
}

function somarTudo(...nums: number[]): number {
  let total = 0;
  for (const n of nums) total += n;
  return total;
}

type Operacao = (a: number, b: number) => number;

const multiplicar: Operacao = (a, b) => a * b;

function aplicar(fn: (n: number) => number, valor: number): number {
  return fn(valor);
}

@@module ts-modelagem | ts | Modelando dados | Interfaces, uniões, narrowing e uniões discriminadas: o coração do TypeScript.

@@lesson ts-objetos-interfaces | Objetos, interfaces e type | 25
@@body
Para descrever a forma de um objeto, use `interface` ou `type`:

```ts
interface Usuario {
  id: number;
  nome: string;
  email?: string;            // opcional
  readonly criadoEm: Date;   // não pode ser reatribuído
}

const u: Usuario = { id: 1, nome: "Ana", criadoEm: new Date() };
// u.criadoEm = new Date();   // erro: Cannot assign to 'criadoEm' because it is a read-only property
```

- Propriedade **faltando** ou **de tipo errado** gera erro.
- Propriedade **a mais** em um objeto literal também gera erro (*excess property check*).

### Estendendo

```ts
interface Admin extends Usuario {
  permissoes: string[];
}

type ComRotulo = Usuario & { rotulo: string };   // interseção
```

### Assinatura de índice

Para objetos de chaves dinâmicas: `interface Mapa { [chave: string]: number }` (ou `Record<string, number>`).

### `interface` ou `type`?

Quase sempre intercambiáveis para objetos. Convenção comum: `interface` para formas de objetos e classes (podem ser estendidas e "reabertas"), `type` para uniões, tuplas e tipos derivados. O importante é ser consistente no projeto.

@@lesson ts-unioes-literais | Uniões e tipos literais | 25
@@body
Uma **união** (`A | B`) diz que o valor pode ser de um tipo **ou** de outro:

```ts
let id: string | number;
id = "abc";   // ok
id = 42;      // ok
// id = true; // erro
```

### Tipos literais

Um tipo pode ser um valor específico. Combinados em união, formam um "enum leve" e seguro:

```ts
type Status = "ativo" | "inativo" | "pendente";
let s: Status = "ativo";
// s = "cancelado"; // erro: Type '"cancelado"' is not assignable to type 'Status'
```

Isso é mais simples que `enum` e some totalmente na compilação.

### Estreitamento (narrowing)

Com uma união, você só pode usar o que **existe em todos** os membros, até **verificar** o tipo:

```ts
function descrever(v: string | number): string {
  if (typeof v === "string") {
    return v.toUpperCase();   // aqui v é string
  }
  return v.toFixed(2);        // aqui v é number
}
```

O TS acompanha o fluxo: depois do `if` com `return`, ele sabe que `v` só pode ser `number`. Outras formas de estreitar: `===`, `in`, `instanceof`, `Array.isArray` e verificar `truthy`.

  switch (d) {
    case "norte": return "leste";
    case "leste": return "sul";
    case "sul": return "oeste";
    case "oeste": return "norte";
  }

function descrever(valor: string | number): string {
  if (typeof valor === "string") return valor.toUpperCase();
  return valor.toFixed(2);
}

@@lesson ts-narrowing-unknown | unknown e type guards | 25
@@body
Dados que vêm de fora do programa (JSON de uma API, um formulário, `localStorage`) **não têm tipo garantido**. O tipo seguro para isso é `unknown`.

```ts
let dado: unknown = JSON.parse('{"a":1}');
// dado.a;               // erro: 'dado' is of type 'unknown'
if (typeof dado === "object" && dado !== null && "a" in dado) {
  console.log(dado.a);   // agora pode
}
```

Com `any`, o erro nunca apareceria, e o programa quebraria em produção. Com `unknown`, o compilador **obriga** a verificar.

### Type guards (funções de guarda)

Uma função cujo retorno é um **predicado de tipo** (`x is T`) ensina o compilador a estreitar:

```ts
function ehTexto(x: unknown): x is string {
  return typeof x === "string";
}

function tamanho(x: unknown): number {
  return ehTexto(x) ? x.length : 0;   // aqui x é string
}
```

### Ferramentas de estreitamento

`typeof x === "number"`, `x instanceof Date`, `Array.isArray(x)`, `"campo" in obj`, `x === null` e comparações com literais.

> O compilador confia no que o seu guarda afirma. Se o guarda mentir, o erro reaparece em tempo de execução. Escreva guardas com cuidado.
@@task
Implemente: `ehString(x: unknown): x is string`; `processar(entrada: unknown): string` (texto → `trim()`; número → `String(n)`; array → itens unidos por `", "`; qualquer outra coisa → `"desconhecido"`); e `parseIdade(texto: unknown): number | null` (devolve o número se for um texto de inteiro entre 0 e 150, senão `null`).
@@starter
function ehString(x: unknown): boolean {
  return typeof x === "string";
}

function processar(entrada: unknown): string {
  return "desconhecido";
}

function parseIdade(texto: unknown): number | null {
  return null;
}

$t('processar([1, "a", 2]) = "1, a, 2"', () => $eq(processar([1, 'a', 2]), '1, a, 2'));

@@types

## ehString recebe unknown

## processar devolve string

@@hints
- A assinatura do guarda é: function ehString(x: unknown): x is string
- Em processar, estreite com typeof e Array.isArray antes de usar métodos.
- parseIdade: confirme que é string e que combina com /^\d+$/; converta com Number e confira o intervalo.
@@solution
function ehString(x: unknown): x is string {
  return typeof x === "string";
}

function processar(entrada: unknown): string {
  if (ehString(entrada)) return entrada.trim();
  if (typeof entrada === "number") return String(entrada);
  if (Array.isArray(entrada)) return entrada.join(", ");
  return "desconhecido";
}

function parseIdade(texto: unknown): number | null {
  if (!ehString(texto) || !/^\d+$/.test(texto)) return null;
  const n = Number(texto);
  return n >= 0 && n <= 150 ? n : null;
}

@@lesson ts-unioes-discriminadas | Uniões discriminadas | 30
@@body
O padrão mais poderoso do TS: modelar estados diferentes como uma união em que cada membro tem uma propriedade-**etiqueta** (`tipo`, `kind`, `status`) com um valor literal.

```ts
type Estado =
  | { status: "carregando" }
  | { status: "sucesso"; dados: string[] }
  | { status: "erro"; mensagem: string };

function mostrar(e: Estado): string {
  switch (e.status) {
    case "carregando": return "Aguarde...";
    case "sucesso":    return e.dados.join(", ");   // aqui só existe .dados
    case "erro":       return e.mensagem;           // aqui só existe .mensagem
  }
}
```

Dentro de cada `case`, o TS sabe exatamente qual membro é, e só deixa usar as propriedades dele. Isso torna **estados impossíveis impossíveis de escrever**: não existe um `{ status: "carregando", mensagem: ... }`.

### Verificação de exaustividade

Se você adicionar um novo estado e esquecer de tratá-lo, o compilador deve avisar. O truque é atribuir o valor restante a `never`:

```ts
function falhar(x: never): never {
  throw new Error("Caso não tratado: " + JSON.stringify(x));
}
// no switch: default: return falhar(e);
```

Se todos os casos foram tratados, `e` é `never` no `default`. Se faltar um, vira erro de compilação.

type Forma =
  | { tipo: "circulo"; raio: number }
  | { tipo: "quadrado"; lado: number }
  | { tipo: "retangulo"; largura: number; altura: number };

function area(f: Forma): number {
  switch (f.tipo) {
    case "circulo": return Math.PI * f.raio ** 2;
    case "quadrado": return f.lado ** 2;
    case "retangulo": return f.largura * f.altura;
    default: {
      const _exaustivo: never = f;
      return _exaustivo;
    }
  }
}

@@body
Tipos também podem ser **calculados**, como funções de tipos.

### Tipos mapeados

Percorrem as chaves de um tipo e geram um novo:

```ts
type Opcionais<T> = { [K in keyof T]?: T[K] };   // é o Partial
type Somente<T> = { readonly [K in keyof T]: T[K] };  // é o Readonly
type Mutavel<T> = { -readonly [K in keyof T]: T[K] }; // o "-" remove o modificador
```

Com `as`, você filtra ou renomeia chaves:

```ts
type SoNumeros<T> = {
  [K in keyof T as T[K] extends number ? K : never]: T[K];
};
```

### Tipos condicionais

`T extends U ? X : Y` escolhe um tipo conforme uma condição:

```ts
type ETexto<T> = T extends string ? "sim" : "não";
type A = ETexto<"oi">;   // "sim"
type B = ETexto<42>;     // "não"
```

### `infer`: capturar um pedaço do tipo

```ts
type Desembrulhar<T> = T extends Promise<infer U> ? U : T;
type X = Desembrulhar<Promise<number>>;   // number

type ElementoDe<T> = T extends (infer E)[] ? E : never;
type Y = ElementoDe<string[]>;            // string
```

@@lesson ts-config-estrito | tsconfig e o modo estrito | 15
@@body
O arquivo **`tsconfig.json`** diz ao compilador como checar e o que gerar. Um ponto de partida moderno:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "skipLibCheck": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true
  },
  "include": ["src"]
}
```

### `strict: true`: o que liga

É um atalho para várias checagens. As mais importantes:

- `strictNullChecks`: `null` e `undefined` não cabem em qualquer tipo. Acaba com o clássico "Cannot read properties of undefined".
- `noImplicitAny`: obriga a anotar quando o TS não consegue inferir.
- `strictFunctionTypes` e `strictBindCallApply`: checagem correta de funções.
- `strictPropertyInitialization`: campos de classe precisam ser inicializados.
- `useUnknownInCatchVariables`: a variável do `catch` é `unknown`.

**Projetos novos devem começar com `strict: true`.** É muito mais difícil ligar depois.

### Flags extras valiosas

- `noUncheckedIndexedAccess`: `lista[0]` passa a ser `T | undefined`, refletindo que o índice pode não existir.
- `exactOptionalPropertyTypes`: distingue "ausente" de "presente como undefined".
- `noImplicitReturns` e `noFallthroughCasesInSwitch`: pegam descuidos.

### Importar só tipos

```ts
import type { Usuario } from "./tipos";
```

`import type` é apagado na compilação. Com `verbatimModuleSyntax`, o TS exige que você seja explícito.

### Outros conceitos de projeto

- **`.d.ts`:** arquivos que só descrevem tipos. Pacotes do npm sem tipos próprios têm tipos em `@types/nome`.
- **`satisfies`:** valida que um valor cabe em um tipo **sem alargar** o tipo inferido.
- **Linters:** `typescript-eslint` acrescenta regras como "proíba `any` explícito".
- **Versões:** em julho de 2026 saiu o TypeScript 7, com compilador nativo, bem mais rápido. A linguagem que você aprendeu aqui é a mesma. O compilador no navegador deste site é o da série 5.x.

> Esta lição é de leitura. Experimente instalar localmente: `npm install -D typescript` e `npx tsc --init`.

@@lesson ts-projeto-result | Projeto: tipo Result e validação | 45
@@body
Hora de juntar tudo: genéricos, uniões discriminadas, narrowing e `unknown`. Vamos construir o tipo **`Resultado`**, um padrão profissional para operações que podem falhar **sem lançar exceções**.

```ts
type Resultado<T, E = string> =
  | { ok: true; valor: T }
  | { ok: false; erro: E };

function sucesso<T>(valor: T): Resultado<T, never> {
  return { ok: true, valor };
}
function falha<E>(erro: E): Resultado<never, E> {
  return { ok: false, erro };
}
```

Quem recebe um `Resultado` é **obrigado** a verificar `ok` antes de acessar `valor`:

```ts
const r = dividir(10, 0);
if (r.ok) {
  console.log(r.valor);   // number
} else {
  console.log(r.erro);    // string
}
// r.valor;               // erro: Property 'valor' does not exist on type '{ ok: false; ... }'
```

O compilador impede de ignorar o caminho de erro. Linguagens como Rust usam exatamente essa ideia.

### Validando dados externos

Dados de fora são `unknown`. Uma função de validação os transforma em um tipo confiável, ou devolve a falha com a explicação. É a base de bibliotecas como Zod, em versão mínima.

@@solution
interface Usuario {
  nome: string;
  idade: number;
}

type Resultado<T, E = string> =
  | { ok: true; valor: T }
  | { ok: false; erro: E };

function sucesso<T>(valor: T): Resultado<T, never> {
  return { ok: true, valor };
}

function falha<E>(erro: E): Resultado<never, E> {
  return { ok: false, erro };
}

function dividir(a: number, b: number): Resultado<number> {
  if (b === 0) return falha("divisão por zero");
  return sucesso(a / b);
}

function mapear<T, U, E>(r: Resultado<T, E>, fn: (valor: T) => U): Resultado<U, E> {
  if (!r.ok) return r;
  return sucesso(fn(r.valor));
}

function validarUsuario(dado: unknown): Resultado<Usuario> {
  if (typeof dado !== "object" || dado === null) return falha("dado inválido");
  const campos = dado as Record<string, unknown>;
  const { nome, idade } = campos;
  if (typeof nome !== "string" || nome.length === 0) return falha("nome inválido");
  if (typeof idade !== "number" || !Number.isInteger(idade) || idade < 0) return falha("idade inválida");
  return sucesso({ nome, idade });
}

@@lesson ts-boas-praticas | Boas práticas e próximos passos | 15
@@body
O que times profissionais de TypeScript costumam adotar:

### Tipos

1. **`strict` sempre ligado.** Sem exceção em projeto novo.
2. **Evite `any`.** Use `unknown` e estreite. Se precisar de `any`, comente por quê.
3. **Deixe o TS inferir** o que for óbvio; **anote** assinaturas públicas (parâmetros e retornos de funções exportadas).
4. **Prefira uniões de literais a `enum`** na maioria dos casos: são mais simples e somem na compilação.
5. **Derive tipos de valores** (`as const`, `typeof`, `keyof`) em vez de duplicar listas.
6. **Modele estados com uniões discriminadas**, de modo que estados inválidos não possam ser representados.
7. **Cuidado com `as`.** Uma asserção de tipo é uma promessa que o compilador não confere. Use só na fronteira (depois de validar) e prefira type guards.
8. **`@ts-expect-error` em vez de `@ts-ignore`:** o primeiro avisa quando deixar de ser necessário.

### Fronteiras

Dados que entram (API, formulário, arquivo, variável de ambiente) são `unknown` até serem **validados**. Bibliotecas como **Zod** ou **Valibot** definem o esquema uma vez e derivam o tipo estático dele.

### Ferramentas

- **ESLint + typescript-eslint** para regras de qualidade.
- **Prettier** para formatação automática.
- **Vitest** para testes (inclusive de tipos, com `expectTypeOf`).
- **tsc --noEmit** na integração contínua para barrar erros de tipo.
